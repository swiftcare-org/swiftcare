# SWC-136 — Sprint 4 local performance results

## Outcome

- **Smoke:** PASS
- **SWC-128 concurrent Call Next:** PASS at 2, 10 and 25 simultaneous doctors
- **Comparable Sprint 3 baseline:** PASS at 20 users
- **Expanded Sprint 4 load:** PASS at 40 users
- **Comparable Stress:** **BLOCKED — insufficient host resources**
- **Highest verified concurrency:** **40 users**

Stress was deliberately not run. At the execution-time capacity gate, before any Stress
traffic, Windows reported only 1.79 GiB free physical memory while the shared QA environments
and isolated SWC-136 stack were active. Running the capped profile under that condition risked
host resource exhaustion and disruption to unrelated QA work. This is a test-environment
limitation, not an application failure and not a passing stress result.

## Environment and isolation

- Branch: `test/SWC-136-sprint4-performance`
- Base: `91936f3`
- JMeter: 5.6.3 on Java 21
- Host: Windows, 16 logical CPUs, 15.71 GiB physical memory
- Docker allocation: 16 CPUs, 7.61 GiB memory
- Compose project: `swiftcare-swc136`
- Gateway under test: `http://127.0.0.1:8016`
- Dedicated network, volume, ports, database names and Kafka consumer groups were used.
- Azure and the shared Gateway on port 8000 were never targeted.

The six thresholds were registered before execution:

- Read p95 <= 800 ms
- Read p99 <= 1500 ms
- Write p95 <= 1500 ms
- Write p99 <= 3000 ms
- Functional error rate <= 0.5%
- Latency drift <= 20%

## Sprint 3 methodology comparison

| Phase | Sprint 3 SWC-126 evidence | Sprint 4 SWC-136 status |
| --- | --- | --- |
| Smoke | 1 Doctor + 1 Receptionist, 1 s ramp, 60 s; 55 samples, 0 failures, 17 labels | 1 thread in each of 6 groups, 6 s ramp, 90 s; 174 samples, 0 failures, 30 labels — **completed** |
| Load | 10 Doctor + 10 Receptionist, 30 s ramp, 900 s; 5,161 samples, 0 errors | Comparable 10 + 10 baseline with the same ramp/duration, then a separate 40-user Sprint 4 mix — **completed** |
| Stress | One 150 Doctor + 150 Receptionist run, linear 0→300 ramp over the complete 600 s duration; 23,251 samples; knee inferred at 46–62 active users | Corrected plan: one six-group 0→300 linear ramp over 600 s — **not executed; BLOCKED** |

The Sprint 3 repository contains no evidence of 50-user or 100-user stress increments. Its
performance triggers were used to locate the knee from the completed time series, while safety
conditions remained the reason to abort early. SWC-136's completed Smoke, baseline and Load
results are unchanged by correcting the unexecuted Stress method.

The measurement exclusions differ: Sprint 3 discarded 60 seconds from run start (30-second
ramp plus 30 seconds of steady state), whereas SWC-136 pre-registered a 90-second exclusion.
The 90-second summaries remain the official SWC-136 verdict. A read-only reanalysis of the
existing JTLs with Sprint 3's 60-second exclusion also passes: the 20-user baseline has 3,784
read samples at 58/71 ms p95/p99 and 1,056 writes at 72/83 ms; the 40-user load has 8,461 reads
at 50/63 ms and 1,170 writes at 69/78 ms. Both have 0% functional errors. The comparison
summaries are committed separately and do not replace the pre-registered result.

## Stress status and saturation finding

The initial SWC-136 draft proposed separate 100, 200, 300 and 400-user stages. A later
read-only methodology review found that this did not match the actual Sprint 3 approach.
Sprint 3 used one 300-user run (150 Doctor + 150 Receptionist), ramped linearly over the whole
600-second duration, and inferred the knee from 30-second active-thread time-series windows;
it did not use fixed 50-user or 100-user increments.

The corrected future SWC-136 profile is one 300-user, six-group linear ramp over 600 seconds:
75 Doctor, 60 Counter, 60 Activity Feed, 60 History, 30 Reports and 15 Admin. It preserves the
Sprint 4 endpoint coverage and the 25:20:20:20:10:5 role ratio. This correction changes only
the planned, unexecuted Stress method; it does not reinterpret any completed result.

No original stage or corrected Stress profile was started because the required host-capacity
gate failed at 1.79 GiB free physical memory. Therefore:

- No stress latency, throughput or error result exists.
- No first saturated service can be identified from a stress run.
- Kafka and AuthService are candidates based on transient load-phase CPU peaks, but this is
  not proof of saturation.
- The verified capacity statement is limited to the successful 40-user load workload.

Run the corrected 300-user continuous-ramp Stress profile later on a dedicated host with
enough free memory for the Docker allocation, JMeter heap and operating-system headroom. Let
the full ramp complete so its knee can be calculated from the same sustained aggregate-p95,
error-rate and throughput signals used in Sprint 3. Abort early only for unsafe host/Docker
pressure or contact with a non-isolated endpoint. Run integrity checks afterward. An optional
400-user continuous-ramp extension is warranted only when 300 users finds no knee and the host
still has safe headroom.

## Limitations

- Stress testing is **BLOCKED**, so no saturation point or capacity claim above 40 users is made.
- Results are specific to this local Windows/Docker host and are not Azure measurements.
- CPU percentages above 100% represent multi-core Docker usage.
- The initial successful 20-user run lacked resource evidence; the accepted rerun replaced it.
- The attempted first 40-user launch produced no traffic because the command-line host
  property was unquoted; the accepted rerun replaced it.
