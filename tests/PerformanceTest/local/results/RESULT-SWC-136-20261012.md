# SWC-136 — Sprint 4 local performance results

## Outcome

- **Smoke:** PASS
- **SWC-128 concurrent Call Next:** PASS at 2, 10 and 25 simultaneous doctors
- **Comparable Sprint 3 baseline:** PASS at 20 users
- **Expanded Sprint 4 load:** PASS at 40 users
- **Staged Stress:** **BLOCKED — insufficient host resources**
- **Highest verified concurrency:** **40 users**

Stress was deliberately not run. Before the first 100-user stage, Windows reported only
1.79 GiB free physical memory while the shared QA environments and isolated SWC-136 stack
were active. Running the capped stage under that condition risked host resource exhaustion
and disruption to unrelated QA work. This is a test-environment limitation, not an
application failure and not a passing stress result.

## Environment and isolation

- Branch: `test/SWC-136-sprint4-performance`
- Base: `91936f3`
- JMeter: 5.6.3 on Java 21
- Host: Windows, 16 logical CPUs, 15.71 GiB physical memory
- Docker allocation: 16 CPUs, 7.61 GiB memory
- Compose project: `swiftcare-swc136`
- Gateway under test: `http://127.0.0.1:8016`
- Dedicated network, volume, ports, database names and Kafka consumer groups were used.
- Azure and the shared Gateway on port 8000 were never targeted.

The six thresholds were registered before execution:

- Read p95 <= 800 ms
- Read p99 <= 1500 ms
- Write p95 <= 1500 ms
- Write p99 <= 3000 ms
- Functional error rate <= 0.5%
- Latency drift <= 20%

## Smoke gate

The final Smoke run used one thread in each of the six Sprint 4 groups for 90 seconds.

- Samples: 174
- Distinct labels exercised: 30
- Failed samples: 0
- Minimum/maximum elapsed time: 6/1463 ms
- Post-run integrity: all 15 checks returned zero violations
- Result: **PASS**

Two preflight attempts are retained as diagnostic evidence and are not counted as test
results. The first exposed Java 24/Groovy incompatibility; the second exposed request/DTO
contract mismatches in the test plan. Both were corrected before the final Smoke gate.

window; its database writes are covered by the integrity report.

Result: **PASS**.

## Stress status and saturation finding

The pre-registered stages were 100, 200, 300 and 400 total users on capped services. The
first 100-user stage was not started because the required host-capacity gate failed: only
1.79 GiB physical memory remained free. Therefore:

- No stress latency, throughput or error result exists.
- No first saturated service can be identified from a stress run.
- Kafka and AuthService are candidates based on transient load-phase CPU peaks, but this is
  not proof of saturation.
- The verified capacity statement is limited to the successful 40-user load workload.

Run staged Stress later on a dedicated host with enough free memory for the Docker allocation,
JMeter heap and operating-system headroom. Use the committed caps and stop at the first
sustained latency/error breach, flat or falling throughput, unsafe host pressure or integrity
violation.

## Limitations

- Stress testing is **BLOCKED**, so no saturation point or 100–400-user capacity claim is made.
- Results are specific to this local Windows/Docker host and are not Azure measurements.
- CPU percentages above 100% represent multi-core Docker usage.
- The initial successful 20-user run lacked resource evidence; the accepted rerun replaced it.
- The attempted first 40-user launch produced no traffic because the command-line host
  property was unquoted; the accepted rerun replaced it.
